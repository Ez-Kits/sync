# Collections and writes

A **collection** is a kind of record your app syncs, such as `todos` or `projects`. Each collection is backed by one table and has a **primary key**. You define collections once and pass them to both the DB adapter and the sync client.

## Define a collection

### With Drizzle

```ts
import { defineDrizzleCollection } from "@ez-kits/sync-client-drizzle-adapter";
import { todos } from "./db/schema";

export const todosCollection = defineDrizzleCollection({
  name: "todos", // used in the API: client.collections.todos
  table: todos, // a Drizzle table (sqliteTable or pgTable)
  // primaryField: "id", // optional: found from the table's primary key column
});
```

### With TypeORM

```ts
import { defineTypeormCollection } from "@ez-kits/sync-client-typeorm-adapter";
import { Todo } from "./db/schema"; // an @Entity class

export const todosCollection = defineTypeormCollection({
  name: "todos",
  entity: Todo,
  primaryField: "id", // required; must match the entity's @PrimaryColumn
});
```

### Rules for collections

- **Names are unique.** The name is the key in `client.collections` and in every sync event.
- **Use a single-column primary key, ideally a string** such as a UUID. Records are created offline on many devices, so ids must be generated by the client and never collide. `crypto.randomUUID()` is a good default. Composite primary keys are not supported: a write whose primary field is not a string or a number throws a `TypeError`, and so do `get` and `delete` with an object id.
- **Pass the same collections everywhere.** Give the same collection objects to the DB adapter and to `createSyncClient`. Write the array inline (`collections: [todosCollection, projectsCollection]`) or keep it in a variable and pass that to both:

  ```ts
  const collections = [todosCollection, projectsCollection];
  ```

## Write records

Every collection gets these methods on `client.collections.<name>`:

```ts
const { todos } = client.collections;

// Create. Pass the full record, including the primary key.
await todos.insert({
  id: crypto.randomUUID(),
  title: "Write docs",
  completed: false,
  updatedAt: Date.now(),
});

// Update. Pass the primary key and only the fields that change.
await todos.update({ id, completed: true, updatedAt: Date.now() });

// Delete by primary key.
await todos.delete(id);
```

Each call:

- runs in **one transaction** with its outbox entry, so the write and its "to be pushed" note are saved together,
- resolves when the write is **saved locally** (not when it reaches the server),
- refreshes live queries in **every tab**,
- is pushed to the backend later, when sync is running and online.

You can call these from **any tab**, leader or follower. A follower's write is forwarded to the leader.

> **Always write through `client.collections`.** A write made with the ORM directly, for example `dbAdapter.db.insert(todos).values(...)`, is not recorded in the outbox. It is never pushed, and live queries do not notice it.

### Good habits

- **Keep an `updatedAt` field** set to `Date.now()` on every write. It makes [conflict resolution](conflict-resolution.md) with `lastWriteWins` easy, and makes incremental pulls possible.
- **Do not wait on the network.** Writes are local; show the result right away. Sync status is a separate concern (see [Syncing](syncing.md)).
- **Bulk inserts** are one transaction each. For thousands of records, insert in a loop and yield now and then (`await new Promise((r) => setTimeout(r, 0))`) so the page stays responsive.

## Errors when writing

A write can reject when:

- the database rejects it (a constraint, a missing table, a wrong column). Fix the data or your schema.
- the storage is not ready, for example the worker failed to open the database. See [Troubleshooting](troubleshooting.md).
- the leader tab changed in the middle of the write. EzSync retries this case for you (up to 3 attempts) and checks whether the first attempt already landed, so a write is never applied twice. You only see `LeaderChangedError` if all attempts fail.

## Deletes and the backend

A local delete removes the row locally and pushes a **delete event**. How the backend stores a delete is up to the sync adapter. The Firebase adapters keep a **tombstone** (`deleted: true`, `deletedAt`) so other devices learn about the delete. See [Sync with Cloud Firestore](firestore.md#deletes).
